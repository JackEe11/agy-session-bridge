# 设计说明

## 为什么不做"每轮重发全部历史"

那是最直觉的做法，但会把 115 层的对话压在 192KB 的漏斗里：每轮都要丢弃最旧的内容，**记忆随对话增长而单调衰减**。

而 `--conversation` 把历史交给 CLI：每轮只发增量，历史由 CLI 累积并用 auto-compact 管理。代价是**一致性责任转移到桥接身上**——酒馆里的编辑/swipe/回滚，CLI 是不知道的。整个 `session.js` 就是为这件事而存在。

## chatKey：为什么是 primary + alias 双键

第一版只用「system 前 1KB + 首条 + 第二条非 system 消息」做哈希，结果第一轮和第二轮算出不同的键：

```
轮 1（只有 1 条非 system）：second = '__INIT__'
轮 2（3 条非 system）    ：second = assistant 的回复
→ 键变了 → 判定 deep → 每轮新建会话 → 会话模式完全失效
```

修复方案：

- **primary** = `sha256(system 前 1KB + 首条非 system)` —— 建会话后永不变化
- **alias** = `sha256(... + 第二条非 system || '__INIT__')` —— 用于建立后索引
- 查询时先 primary 后 alias；命中后把两个键都并入记录的 `keys[]`

为什么不一上来就用 primary：两个聊天如果开场白完全相同（同一角色卡开两个档），primary 会撞键。alias 把"第二句"纳入进来，能区分开；而 primary 保证稳定性。两者互补。

**为什么只取 system 前 1KB**：世界书（World Info）与 Author's Note 会随轮次动态插入 `system`，取全文会让键每轮漂移；取前 1KB 又能避开"同名角色不同卡"。

## 漂移三态

| 状态 | 触发 | 动作 | 理由 |
|---|---|---|---|
| `advance` | 楼层哈希前缀一致，且只多 1 条 | 发最新 user 消息 | 最常见路径，零成本 |
| `shallow` | 首个不一致下标距尾部 ≤ 4 层，且 swipeStreak < 3 | `[TIMELINE OVERRIDE]` + 分叉点起真值 | swipe 重抽占漂移的 90%，重建太贵 |
| `deep` | 回滚 > 4 层 / 切分支 / 会话失效 | 三明治 bootstrap 重建 | 局部纠正已不可靠 |

**为什么 `shallow` 要限 3 次**：作废的旧回复仍留在 CLI 历史里，累积会污染文风；超过 3 次直接重建更干净。

## 三明治 bootstrap

```
[SYSTEM]   完整 system            ← 人设与规则的根基
[OPENING]  开场前 2 层            ← 定基调
[TIMELINE] timeline.md 归档        ← 保全书因果链（每条 0.3-0.6KB，比原文省 10 倍）
[RECENT]   从尾部往前装到 170KB    ← 保当前场景细节与文风
```

为什么不直接把最旧的几层也塞进去：115 层原文约 860KB，天花板 192KB。**归档 + 近期原文**是同等预算下信息密度最高的组合。

更早的原文不进 prompt，但会以 `archive_*.md` 存在工作区里，模型需要时可以按路径查阅（文件工具在 `--add-dir` 内可用）。

## `<ta_record>`：流式剥离的两个难点

1. **标签会被拆到多个 delta**：`<ta_rec` + `ord>...`。解法是保留 24 字节 holdback，遇到不完整的标签前缀就不往下发。
2. **不能事后剥离**：SSE 已经发出去了，用户会看到归档块。所以必须在流式过程中判断。

`recordFilter().push(delta)` 返回"此刻可以安全发送的文本"，`flush()` 在结尾补上剩余的安全部分（并吞掉未闭合的标签）。

## 归档的幂等与回滚

`timeline.md` 每条前面写 `<!-- floor: N -->`。写入 `floor N` 时先删除所有 `floor >= N` 的段，再追加。

- 重复写同一层 → 不会重复
- 回滚到旧层 → 更高楼层自动截断
- swipe 重抽 → 覆盖该层而非新增

## 并发：为什么是抢占而不是排队

同一聊天的两个请求（酒馆重试、用户连点）如果排队执行，**CLI 历史里会连续写入两轮相同的提问与回复**，楼层直接错乱。

所以策略是：同 key 新请求 → `SIGTERM` 旧进程 → 300ms 后仍占用则返回 429。跨聊天则进全局队列（并发 1，容量 2）。

全局并发锁 1 的直接依据是实测内存：单轮 `agy` 峰值 305MB，1.9GB 的机器上并发 2 就会逼近 OOM。

## 失效检测

三个信号叠加：

1. 本地文件：`brain/<convId>/.system_generated/logs/chunks/transcript/` 是否存在且非空（<1ms，零成本）
2. 运行时：输出里出现 `warning: conversation "<id>" not found`（CLI 会静默新建，不看这条就会误以为还在原会话）
3. 结构性：模型换过（`sess.model !== 当前 model`）→ 主动校验
4. 软失效：`turns > 1` 但输出里少了 `<ta_record>`，多半意味着落到了空会话

任何一条命中 → 当前请求内透明回退到 bootstrap 重建，用户无感。

## 双模式与回滚

`AGY_SESSION_MODE=0` 时完全走旧的无状态逻辑（每轮拼全量历史 + 滚动摘要）。

保留它的原因：会话模式虽然更好，但它把"一致性"责任放在了桥接侧。真出问题时，一条环境变量就能退回到行为可预测的旧模式，比回滚代码快。
